## Règles

- ❌ Ne jamais identifier une erreur par son message (traduit) : utiliser un code.
- ❌ Ne jamais concaténer des fragments traduits : une clé = une phrase complète.
- ✅ Toute chaîne visible passe par un catalogue (`src/locales/{fr,en}/`) ; `npm run i18n:scan` détecte les oublis.
- ✅ Toute nouvelle clé se traduit vraiment dans `en` : `npm run i18n:identical` refuse une valeur recopiée du français non déclarée légitime.
- ✅ Un terme produit se traduit par son terme épinglé (`objectif` → `objective`, jamais `goal`) : `npm run i18n:quality` refuse l'écart.
- ✅ Orthographe de `en` : anglais américain (`color`, `organize`), sauf `legal`, `legalTerms`, `legalPrivacy` (contrats, le français fait foi, orthographe britannique, modifications soumises à `check:legal-journal`).
- ✅ Vocabulaire `en` : « Calendar » (pas « Agenda »), « Company mode » / « company space », « Timeline », « Key result ».
- ✅ Avant d'ouvrir une langue à l'indexation, vérifier que le contenu éditorial (blog, cas d'usage, prérendu) est traduit, pas seulement l'interface.
- ✅ Le moteur retombe clé par clé sur `fr` : une clé oubliée n'affiche jamais de clé brute, mais s'affiche en français dans une interface anglaise.
- ✅ Contenu éditorial : `src/content/use-cases.mjs` et `src/content/blog/*.mjs` portent un corps `en` ; `availableLocales()` (`prerender/page.ts`) ne publie une locale que si elle a méta ET contenu. Les trois pages contractuelles ont un résumé EN `noindex` (`prerender/content/short-pages.ts`).
- ✅ `es` est déclaré dans `ALL_LOCALES` et `route-slugs.json` mais absent de `SUPPORTED_LOCALES` : non servi, mécanisme prévu.

## Gardes

```bash
npm run i18n:check       # parité des clés fr ↔ en (CI, bloquant) ; vérifie aussi les règles noindex de vercel.json
npm run i18n:scan        # chaînes en dur non externalisées (GATE CI, cliquet à 0) ; -- --list dit lesquelles
npm run i18n:identical   # valeurs en identiques au fr non déclarées (GATE CI, cliquet à 0) ; -- --list
npm run i18n:quality     # glossaire épinglé et français résiduel dans en (bloquante dans lint-test-build)
npm run i18n:namespaces  # catalogues rendus par le shell (eager) ; --pages : liste à déclarer par route dans App.tsx
npm run profile:landing  # profil du fil principal (CPU bridé, Playwright)
```

- ❌ Ne JAMAIS relever `MAX_STRINGS` (`i18n:scan`) ni `MAX_UNDECLARED` (`i18n:identical`) pour faire passer la CI : une nouvelle chaîne ou identité se traite.
- ❌ Ne jamais énoncer « plus aucune chaîne en dur dans `src/` » : le seul énoncé vérifiable est la sortie de `i18n:scan -- --list`.
- ✅ `i18n:scan` exclut deux choses assumées : les commentaires de code et les seeds de démo (français de référence, recouvert par `localizeSeed` / `isEnglishSeed`). Il couvre le texte JSX avec interpolation, le texte multiligne, les propriétés d'objet `label:` et les valeurs par défaut de prop.
- ⚠️ `i18n:check` ne voit que les clés, jamais leur contenu.
- ⚠️ `profile:landing` : sur un poste de dev la charge machine domine, un écart entre deux pages ne se lit que sur le runner ; l'outil sert à comparer un avant/après sur la même page.

### `i18n:identical`

Allowlist : `scripts/i18n-identical-allowlist.json`, une entrée par clé avec catégorie et valeur `fr` épinglée. Catégories : `mot-identique`, `anglicisme-fr`, `symbole-ou-format`, `sigle`, `nom-propre`, `identifiant-technique`.

- ✅ Le script échoue si une entrée ne correspond plus à aucune clé, a fini par être traduite, porte une valeur `fr` différente de celle épinglée (sans cela, renommer « Manager » ferait hériter la nouvelle chaîne de l'ancienne dispense), ou cite une catégorie inconnue.
- ❌ Ne jamais déclarer légitime une phrase : les catégories couvrent des mots, sigles, formats et noms ; une phrase identique n'est pas traduite.
- ✅ Témoin : `scripts/i18n-identical.guard.test.mjs`.

### `i18n:quality`

Allowlist : `scripts/i18n-quality-allowlist.json`, une exception par clé, justification d'au moins 20 caractères, valeur épinglée (`fr` pour le glossaire, `en` pour le français). Vérifiée : clé disparue, exception qui ne déclenche plus rien, valeur épinglée changée ou justification absente font échouer la garde.

- ✅ Glossaire épinglé (source `fr` → valeur `en`, cherchés comme radicaux) : `tâche` → `task`, `habitude` → `habit`, `objectif` → `objective`, `résultat clé` → `key result`, `agenda` → `calendar`, `catégorie` → `category`, `équipe` → `team`, `projet` → `project`, `série` → `streak`, `corbeille` → `trash`, `point d'étape` → `check-in`, `palier` → `tier`, `dépendance` → `depend`, `assigné` → `assign`, `organigramme` → `org chart`.
- ✅ Français résiduel dans `en` : ni accent français, ni guillemets `« »`, ni mot outil (`le, la, des, pour, avec…`), ni verbe d'interface (`supprimer, ajouter…`). Les homographes anglais (`son`, `plus`, `on`, `a`, `date`) n'y sont pas.
- ❌ Ne pas épingler un terme qui n'a pas une seule traduction : `entreprise` (organization, company, business), `échéance`, `favori`, `rôle`, `membre`.
- ❌ Ne jamais déclarer une exception pour faire taire la garde : une exception dit pourquoi la traduction est juste, sinon on corrige le catalogue.
- 🔴 Ce qu'elle ne garde pas (relecture humaine `M-50`) : le sens, la grammaire, le registre, l'idiomatique ; un terme hors glossaire ; du français sans accent ni mot de la liste ; le contenu de `src/content/` et `prerender/`.
- ✅ Témoin : `scripts/i18n-quality.guard.test.mjs` ; rejoué par `check:sabotages` (`i18n-traduction-fausse`).
